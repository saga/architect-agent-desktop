# Repository Agent Rules

## Plugin format

- The only supported plugin package format is the official Claude Code Plugin directory format.
- Import plugins using the Claude Code conventions: `.claude-plugin/plugin.json` when a manifest is supplied, and standard component directories such as `skills/`, `commands/`, and `agents/`. Follow the Claude Code specification for optional manifest fields and directory layout.
- Do not create, retain, or restore an application-specific plugin manifest format such as `manifest.json`.
- Do not add backward-compatibility adapters, migration paths, or fallback parsers for the retired application-specific plugin format. Breaking compatibility with that format is intentional; a negative test may assert that the retired format is rejected.
- Keep the importer, runtime metadata, examples, tests, settings UI, and documentation aligned with the Claude Code Plugin format only.
- Treat imported plugin content as untrusted. Importing or enabling a plugin must never execute code.
- Keep runtime approval separate from plugin enablement. Both Copilot SDK and CodeBuddy may receive only enabled, explicitly runtime-approved plugin directories, and only when global Agent permission is allow-all and the active Expert does not narrow that permission. Bind approval to a SHA-256 fingerprint of the complete plugin directory; any content change must invalidate the approval. Disabling/removing a plugin must revoke runtime approval.
- Never evaluate third-party plugin code inside the Electron main process or renderer. Use each provider's native plugin runtime. Do not let plugin Mods or Hooks override the host's permission ceiling, IPC validation, browser restrictions, or dangerous-action policy.
- For Copilot, use SDK RuntimeConnection.forStdio with repeated --plugin-dir arguments at Client startup (do not use SessionConfig.pluginDirectories, which targets Agent Plugins/Open Plugin Spec semantics). Under mode: "empty", expose only the minimum bash, skill, and task built-ins when plugin runtime approval is active, set enableSkills: true, and scope workingDirectory to the selected Workspace or the private app Copilot directory. Apply sandboxConfig before MCP/LSP startup with sandbox enabled, allowBypass false, sandboxMcpServers true and sandboxLspServers true. In the temporary projection, translate CLAUDE_PLUGIN_ROOT to PLUGIN_ROOT; preserve CLAUDE_PLUGIN_DATA because Copilot supports that alias. Copilot Legacy Plugin natively loads Skills, Commands, Agents, Hooks, MCP and LSP. Do not make unsupported sandbox enforcement claims.
- For CodeBuddy, pass repeated --plugin-dir arguments through the SDK query's extraArgs. Remove inherited CODEBUDDY_PLUGIN_DIRS, stage a SHA-256 verified copy per query, and delete it in finally. On macOS/Linux, enable CodeBuddy Bash sandboxing for approved plugin sessions and set allowUnsandboxedCommands: false. This Bash sandbox does not establish isolation for every Hook/MCP/LSP child process; Windows currently lacks the CodeBuddy Bash sandbox.
- Copilot Legacy Plugin natively loads Skills, Commands, Agents, Hooks, MCP, LSP and plugin scripts. Copilot does not implement CodeBuddy Mods. Keep this provider-specific limitation visible in the UI and docs.
- All runtime capabilities need tests for the runtime-approval gate, global permission gate, Expert ceiling, provider gate, source immutability, and revocation.
